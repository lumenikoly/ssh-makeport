# Архитектура MakePort

## Простая модель владения

Один пакет Cargo и один процесс приложения. Модуль `engine` — единственный владелец
профилей, состояния задач и объектов дочерних процессов. Интерфейс отправляет
типизированные команды по ограниченному каналу и получает снимки состояния.
У интерфейса нет доступа к shell или SSH через произвольные строки команд.

```text
Slint (главный поток)
    │ Action / View
    ▼
Engine (один рабочий поток)
    ├── Store: config.toml + блокировка экземпляра
    ├── OpenSSH: соединение туннелей
    ├── OpenSSH: чтение Makefile
    └── OpenSSH: задача 1 … задача 8
```

Рабочий поток раз в 30 мс проверяет команды и завершение процессов. Снимки
интерфейса отправляются не чаще одного раза в 80 мс и только при изменениях;
интерфейс забирает последнее состояние раз в 100 мс. Модели списков не создаются
заново при каждом изменении журнала. Никакого локального HTTP-сервера нет.

У каждого SSH-процесса два небольших читающих потока. Очередь вывода ограничена
256 блоками по 4096 байт; при переполнении чтение замедляется, вместо накопления
памяти или потери контрольных сообщений. Это намеренное противодавление для
программ, генерирующих чрезмерный вывод. Буфер одной неполной строки — до 8192 байт.

## SSH, а не собственная реализация протокола

Запускается исполняемый файл OpenSSH напрямую, через `std::process::Command`.
Локальная оболочка команду не интерпретирует. Параметры, целевой узел и удалённая
команда передаются отдельными аргументами.

Удалённая строка проходит POSIX-цитирование: содержимое пути не раскрывает `$`,
обратные кавычки, кавычки и другие конструкции оболочки. `~` раскрывается явно
внутри скрипта, а не за счёт небезопасной подстановки. Имена целей имеют маленький
проверяемый алфавит; аргументы Make и переменные окружения через имя цели не проходят.

Удалённая оболочка пользователя должна уметь запускать POSIX `sh -c`. Полный
интерактивный терминал, Windows PowerShell на сервере и терминальные программы
вроде Vim не поддерживаются. Клиент Windows при этом поддерживается.

`ControlMaster` не используется. Это несколько независимых SSH-соединений,
а не зависимость от платформенно различающихся управляющих сокетов. При восьми
задачах это осознанно небольшой масштаб. Цена — отдельная аутентификация для
каждого процесса; преимущество — независимое владение и остановка.

## Готовность туннелей

Соединение туннелей не использует `ssh -N`. После настройки перенаправлений
оно проверяет папку и наличие Make, печатает уникальный маркер готовности
и остаётся открытым на `cat`, читающем stdin. Закрытие входа завершает соединение.
`ExitOnForwardFailure=yes` не допускает молчаливого частичного успеха при ошибке
привязки порта. Отдельная предварительная проверка порта лишь улучшает диагностику;
она не устраняет гонку с чужими процессами, и окончательное решение принимает SSH.

Открытый порт SSH не доказывает работоспособность конечного веб-сервера.
Сканирования сервисов, угадывания портов по выводу и HTTP-проверок произвольных
портов нет. Это позволяет не отправлять HTTP-запросы, например, в PostgreSQL.

## Жизненный цикл задачи

До запуска в `config.toml` атомарно добавляется `unconfirmed`-запись.
Задача исполняется внутри удалённого PTY; вывод находится под наблюдением приложения.
Успешное создание локального SSH-процесса не равно запуску Make: для перехода
из «Запускается» в «Работает» нужен удалённый маркер начала.

Остановка сначала отправляет байт `0x03`. В PTY включены обработка сигналов и
стандартный символ прерывания. Оболочка ловит, а не игнорирует SIGINT, чтобы
дочерняя команда получила нормальную обработку сигнала. После выхода Make
оболочка печатает подтверждение завершения с кодом выхода.

После получения подтверждения приложение удаляет запись `unconfirmed`. Если
сохранить удаление не удалось, повторный запуск остаётся заблокированным.
Если соединение исчезло без подтверждения, запись остаётся на диске. Даже после
перезапуска клиента задача показывается как неподтверждённая. Ручное подтверждение
тоже сначала сохраняется, а уже потом разблокирует кнопку запуска.

После 8 секунд без завершения при остановке локальный SSH принудительно закрывается.
Состояние не выдаётся за успешную остановку. При закрытии приложения предусмотрено
общее ограничение ожидания; неподтверждённые задачи останутся в конфигурации.

Маркеры — идентификаторы корреляции в уже аутентифицированном канале, **не отдельный
криптографический протокол**. Сервер, пользовательский Makefile и задачи считаются
доверенными. Злонамеренная команда, получившая контроль над удалённым окружением,
может подделывать свой вывод; приложение не является песочницей.

## Что не гарантируется

Нельзя доказать завершение программы на другой машине после потери сетевого
канала. Нельзя гарантированно остановить процессы, самостоятельно покинувшие
терминальную сессию. Нет повторного подключения к журналу старой задачи.
Нет распределённой гарантии единственного запуска, если пользователь запускает
ту же задачу другим SSH-клиентом или с другой машины. Локальная запись защищает
только от случайного повторного запуска через этот экземпляр конфигурации MakePort.

Процесс, который запущен вручную вне приложения, неизвестен MakePort. Пользователь
может подтвердить неизвестное состояние только после собственной проверки сервера.
Автоматический поиск и уничтожение процессов по имени намеренно не реализованы.

## Хранение

`tempfile` создаёт временный файл в той же папке, данные синхронизируются, затем
файл атомарно заменяет `config.toml`. На Unix дополнительно запрашивается
синхронизация родительской папки. `fs2` удерживает блокировку файла экземпляра
на время работы, чтобы два приложения не перезаписывали настройки друг друга.
Файл блокировки не удаляется во время освобождения: удаление создало бы гонку
между разными inode. Неиспользуемый файл безопасно остаётся в папке.

Неизвестная версия, неизвестные поля, дубликаты, невалидные порты и слишком
большой файл дают явную ошибку. Приложение не «чинит» их потерей данных.
Редактирование файла вручную во время работы не отслеживается: для этого
нужно предварительно закрыть MakePort.
