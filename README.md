# MakePort

Небольшое настольное приложение для удалённого проекта: SSH-подключение,
локальные туннели и кнопки запуска целей Makefile в одном окне.

**Клиент:** Windows, macOS, Linux. **Удалённая машина:** Linux, macOS или WSL
с SSH-сервером, POSIX-оболочкой и Make. Windows-сервер с PowerShell в качестве
удалённой оболочки не поддерживается.

Rust + Slint. Один исполняемый файл, системный OpenSSH, локальный TOML.
Нет браузерного движка, JavaScript, базы данных, фоновой службы и устанавливаемого
агента на сервере. Одновременно открыт один проект; разные его задачи могут работать
параллельно.

## Интерфейс для повседневной работы

Настройка проекта проходит в три шага: сервер → папка проекта → приложения.
Адрес сервера и имя пользователя вводятся отдельно. Доступ к приложению добавляется
двумя полями: порт на сервере и, при необходимости, другой порт на этом компьютере.
Синтаксис SSH и запись вида `15432:5432` знать не нужно.

На главном экране есть подсказка следующего действия, поиск задач, понятные состояния
«Готово» и «Ошибка». Описания из Makefile показываются как названия задач;
техническое имя команды остаётся рядом. Журнал и ручной ввод задачи открываются
по запросу. Обновление списка удаляет исчезнувшие цели, сохраняя ручные,
работающие и неподтверждённые задачи.

Для первого входа администратор должен настроить SSH-доступ с этого компьютера
и проверить ключ сервера. MakePort использует существующие ключи и SSH-агент;
интерактивного ввода пароля и файлового браузера сервера пока нет.

## Запуск

Нужны актуальный стабильный Rust с Cargo, средства сборки платформы и OpenSSH 8.9+
в рабочей среде. Rust нужен для сборки, но не для запуска готового приложения.
Проверка версии SSH:

```sh
ssh -V
```

После распаковки:

```sh
cd makeport
cargo run --release
```

Cargo загрузит зависимости, зафиксированные в `Cargo.lock`. Проверяемая сборка:

```sh
cargo build --release --locked
```

`Cargo.lock` включён в проект. Для повторяемой сборки используйте `--locked`.

### macOS

Установите инструменты командной строки Xcode, если их нет:

```sh
xcode-select --install
cargo build --release
python3 scripts/package.py
```

Результат — `dist/MakePort-macos-<архитектура>.zip`, внутри `MakePort.app`.
Сценарий делает локальную подпись приложения, но не нотарификацию Apple.
Для публичного распространения нужен отдельный процесс подписи и нотарификации.

### Windows

Нужны Rust с инструментами MSVC и Visual Studio Build Tools с компонентами C++.
OpenSSH Client устанавливается через дополнительные компоненты Windows.
При необходимости команда в PowerShell администратора:

```powershell
Add-WindowsCapability -Online -Name OpenSSH.Client~~~~0.0.1.0
```

Сборка и запуск:

```powershell
cargo build --release
.\target\release\makeport.exe
python scripts/package.py
```

Приложение в первую очередь ищет системный
`%SystemRoot%\System32\OpenSSH\ssh.exe`, затем абсолютные пути из `PATH`.
Если системный клиент старый, укажите путь к более новому через `MAKEPORT_SSH`.
Локальный `make`, Node.js и pnpm на Windows для запуска удалённых задач не нужны.

### Linux

Для Debian/Ubuntu:

```sh
sudo apt install build-essential pkg-config libfontconfig1-dev \
  libxkbcommon-dev libxkbcommon-x11-dev libwayland-dev \
  libx11-dev libx11-xcb-dev libxcb-shape0-dev libxcb-xfixes0-dev \
  openssh-client
cargo run --release
```

Нужен графический сеанс X11 или Wayland. Для открытия браузера используется `xdg-open`.
Программный рендерер выбран явно; отдельная установка Qt не нужна.

## Первое подключение

Сначала проверьте обычный SSH из терминала. Пример `~/.ssh/config`:

```sshconfig
Host devbox
    HostName 192.168.1.50
    User developer
    IdentityFile ~/.ssh/id_ed25519
```

```sh
ssh devbox
```

Для первого подключения сравните отпечаток ключа сервера с доверенным источником.
Приложение **не принимает неизвестные ключи автоматически** и не отключает проверку
`known_hosts`. Затем проверьте вход без интерактивных запросов:

```sh
ssh -o BatchMode=yes -o StrictHostKeyChecking=yes devbox true
```

Ключ с парольной фразой предварительно загрузите в SSH-агент:

```sh
ssh-add ~/.ssh/id_ed25519
```

В MakePort нажмите **«Добавить проект»**:

1. **Сервер.** Назовите проект, укажите адрес сервера или псевдоним из SSH-настроек.
   Имя пользователя вводится отдельным полем; для готового псевдонима его можно оставить пустым.
2. **Проект.** Введите путь к папке с Makefile, например `~/projects/site`.
   Дополнительные имена задач можно указать в раскрывающемся разделе.
3. **Приложения.** Добавьте порты, которые сообщил автор проекта. Для сайта на порту
   5173 достаточно заполнить поле «Порт приложения на сервере». Для базы данных
   на 5432 с локальным адресом 15432 заполните оба поля. Нажмите «Добавить доступ».
   Если нужны только задачи без доступа к приложению, этот шаг можно пропустить.

Нажмите **«Подключиться»**, чтобы сохранить проект и сразу получить задачи,
или **«Сохранить»**, чтобы подключиться позже. Доступ к приложениям поднимается
вместе с соединением. Уже известную задачу можно запустить без предварительного
подключения: приложение подключится автоматически.

Найдите задачу по названию или имени команды и нажмите **«Запустить»**.
Для длительной задачи доступна кнопка **«Остановить»**. **«Подробности»** открывает
её журнал; его можно скопировать и передать администратору.

В разделе **«Открыть приложение»** отображается адрес на вашем компьютере.
После запуска сайта нажмите **«В браузере»**. Состояние **«Доступ подключён»**
подтверждает SSH-соединение и доступ к порту, но не проверяет, запущен ли сам сайт.
Адрес открытия — `http://127.0.0.1:<порт>/`; для HTTPS или других протоколов
используйте подходящий клиент.

Ошибки подключения дают рекомендацию: проверить адрес/VPN, путь к папке,
имя пользователя либо попросить администратора настроить ключ доступа.
Техническая причина сохраняется в журнале подключения.

## Makefile

Предпочтительный формат — простые именованные цели с `##`:

```makefile
.PHONY: dev test build lint

dev: ## Запустить сервер разработки
	pnpm dev

test: ## Выполнить тесты
	pnpm test

build: ## Собрать приложение
	pnpm build

lint: ## Проверить код
	pnpm lint
```

Перед командами в Makefile нужна **табуляция**, не пробелы.

Если целей с `##` нет, показываются простые имена из `.PHONY`. Можно добавить цели
в настройках или ввести имя вручную. Поддерживаются буквы, цифры, `_`, `-`, `.` и `/`;
имя не может начинаться с `-`. Параметры вида `ENV=dev` и произвольные shell-команды
не принимаются. Для них заведите отдельную цель Makefile.

Приложение не выполняет `make -p`, не вычисляет переменные и не интерпретирует
`include`, `eval`, `define`, шаблонные и генерируемые цели. Только чтение первого
доступного `GNUmakefile`, `makefile` или `Makefile`, максимум 256 КиБ. Для сложных
Makefile используйте явно добавленные цели.

Работающий пример без Node.js находится в [examples/demo](examples/demo).

## Остановка и потеря связи

Задача запускается с удалённым псевдотерминалом (`ssh -tt`). Кнопка **«Остановить»**
отправляет настоящий символ Ctrl+C; терминальный драйвер посылает сигнал группе
переднего плана. Это охватывает Make, обычную оболочку рецепта и обычные дочерние
процессы. Локальный процесс SSH не убивается сразу.

Удалённая оболочка после выхода Make печатает служебное подтверждение с кодом
завершения. Без него приложение не показывает задачу как успешно остановленную.
Через 8 секунд без завершения локальное SSH-соединение принудительно закрывается,
а состояние становится **«Состояние неизвестно»**.

Перед запуском запись о задаче атомарно сохраняется в `config.toml`. Она удаляется
после подтверждённого завершения. Поэтому после аварии приложения или перезапуска
компьютера неподтверждённые задачи остаются заблокированными для повторного запуска.
Проверьте процесс на сервере и нажмите **«Разобраться»**, чтобы снять блокировку.

Самостоятельно отделившиеся процессы (`nohup`, `&`, `setsid`, демонизация),
интерактивные программы и полноэкранные терминальные интерфейсы не входят в эту модель.
`make dev` должен держать сервер на переднем плане. **Нельзя гарантировать уничтожение
произвольного дерева удалённых процессов без удалённого диспетчера**; приложение
не скрывает эту границу.

При временном обрыве ранее установленного соединения предусмотрено до пяти попыток
восстановления туннелей с задержками 2, 4, 8, 16 и 30 секунд. Неудачное самое первое
подключение автоматически не повторяется. **Задачи не перезапускаются автоматически.**
Изменение локального порта во время работы и остановка постороннего процесса
не выполняются: при конфликте выберите другой локальный порт в настройках.

## Окружение SSH

`pnpm`, Node.js и прочие инструменты должны быть доступны **на сервере** из
неинтерактивного SSH-сеанса. Например:

```sh
ssh devbox 'cd "$HOME/projects/site" && command -v pnpm && make --version'
```

Если Node установлен через менеджер версий, настройте окружение в Makefile или
скрипте проекта. MakePort намеренно не угадывает `nvm`/`fnm`/`asdf` и не запускает
пользовательские файлы инициализации наугад.

SSH сохраняет обработку `IdentityFile`, `ProxyJump`, `ProxyCommand`, `Include`,
порта сервера и других параметров вашего доверенного SSH-конфига. Приложение
переопределяет параметры, необходимые для владения процессом: отключает
мультиплексирование, фоновый запуск, агентское перенаправление, X11,
`RemoteCommand` и `LocalCommand`.

В соединении туннелей OpenSSH также учитывает ваши `LocalForward`, `RemoteForward`
и `DynamicForward`, если они есть в `~/.ssh/config`. Не дублируйте там порты,
заданные в MakePort. В соединениях задач и чтения Makefile унаследованные
перенаправления отключаются через `ClearAllForwardings=yes`.

Приложение создаёт **только локальные TCP-туннели `-L`**, привязанные к `127.0.0.1`.
Редактора `-R`, SOCKS и произвольных удалённых адресов в интерфейсе нет.

## Настройки и приватность

Кнопка **«Папка настроек»** открывает платформенную папку `config.toml`.
Профили содержат имя сервера, путь проекта, порты, явные цели и записи
неподтверждённых запусков. Ключи, пароли и журнал вывода туда не копируются.
Обычные журналы хранятся только в памяти; в них могут быть секреты, напечатанные
вашими командами. Перед передачей скопированного журнала проверьте его содержимое.

Запись файла атомарная; второй экземпляр с той же папкой настроек не допускается.
Повреждённый или неизвестный формат конфигурации не заменяется пустым файлом.
Для ручного редактирования сначала закройте приложение.

Переменные окружения для изолированного запуска:

```sh
MAKEPORT_CONFIG_DIR=/absolute/path/to/settings \
MAKEPORT_SSH=/absolute/path/to/ssh \
cargo run --release
```

Автоподключения при старте приложения нет: соединение устанавливается по явному
действию пользователя. Нет телеметрии и автоматической проверки обновлений.
Работа приложения не требует доступа в интернет, если доступна ваша SSH-машина.
Сборка зависимостей, конечно, требует сети либо предварительно заполненного кеша Cargo.

## Разработка и проверки

```sh
cargo test --no-default-features
cargo clippy --all-targets
cargo fmt --all
cargo build --release
python3 -m unittest discover -s tests -p 'test_*.py' -v
```

Тесты ядра не требуют графического окружения. На Unix Rust-интеграционный тест
использует `tests/fake_ssh.py`: запускает настоящие shell-команды и Make в локальном
псевдотерминале, проверяет цикл сохранение → подключение → запуск → остановка.
Это не тест криптографии или совместимости конкретного SSH-сервера.

В `.github/workflows/ci.yml` предусмотрены сборка GUI, проверки ядра и упаковка
для трёх ОС. Они выполнятся после публикации проекта в вашем репозитории.
Windows/Linux собираются под архитектуру исполнителя; macOS также под архитектуру
выбранного исполнителя, не универсальный бинарный файл.

## Ручной выпуск релиза

Workflow **Release** в `.github/workflows/release.yml` запускается только вручную,
как в [JexFold](https://github.com/lumenikoly/JexFold/blob/main/.github/workflows/release.yml).
Введите **новый** тег вида `v0.1.0`. Сборка выполняется из `main`; тег создаётся
после успешной сборки всех платформ. Существующий тег не пересобирается и не перезаписывается.

1. Укажите нужную версию в `Cargo.toml`, обновите `Cargo.lock` командой
   `cargo check --no-default-features` и отправьте изменения в `main`.
2. На GitHub откройте **Actions → Release → Run workflow**.
3. Выберите ветку **main**, введите тег, например `v0.1.0`, и нажмите **Run workflow**.
4. После успешного выполнения готовые файлы появятся в **Releases**.

Для версии `v0.1.0` публикуются непосредственно исполняемые файлы, без ZIP и `.app`:

| Файл | Платформа |
|---|---|
| `MakePort-v0.1.0-windows-x86_64.exe` | Windows x64 |
| `MakePort-v0.1.0-linux-x86_64` | Linux x64 |
| `MakePort-v0.1.0-macos-arm64` | Mac с Apple Silicon |
| `MakePort-v0.1.0-macos-x86_64` | Mac с Intel |

Также прикладывается `SHA256SUMS`. На Linux/macOS после скачивания бинарника
дайте ему право запуска и запустите из терминала, например на Apple Silicon:

```sh
chmod +x MakePort-v0.1.0-macos-arm64
./MakePort-v0.1.0-macos-arm64
```

Mac-бинарники имеют локальную подпись, без Developer ID и нотарификации Apple.
Обычная упаковка через `scripts/package.py` остаётся отдельным локальным сценарием.

Все платформы собираются из одного зафиксированного коммита. Публикация запускается
только после проверок и сборок Windows, Linux и обеих архитектур macOS.
Версия тега должна совпадать с `Cargo.toml` и записью MakePort в `Cargo.lock`.
Рабочий процесс использует штатный `GITHUB_TOKEN`; отдельный PAT не требуется.

## Структура

```text
src/model.rs       Профили, проверки входных данных, записи запусков
src/store.rs       TOML, атомарное сохранение, блокировка второго экземпляра
src/shell.rs       Аргументы OpenSSH и безопасное цитирование
src/process.rs     Владение процессами, ограниченные каналы вывода
src/engine.rs      Состояния соединения, задач, переподключение
src/makefile.rs    Небольшой статический распознаватель целей
src/log.rs         Ограниченные журналы, UTF-8 и удаление ANSI-команд
src/main.rs        Связь интерфейса и ядра
ui/app.slint       Одно окно, редактор проекта, подтверждения
remote/           Встроенные shell-команды; на сервер не устанавливаются
```

Вместо отдельного асинхронного окружения использованы стандартные потоки и
ограниченные каналы Rust. Состоянием владеет один рабочий поток. Чтение stdout/stderr
не блокирует интерфейс. Журнал ограничен 64 КиБ / 1200 строк на задачу; поток вывода
ограничен очередью, длинные строки также имеют верхнюю границу. Максимум 8
одновременных задач, 32 туннеля, 128 целей и 64 сохранённых проекта.

Архитектура и границы гарантий: [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md).
